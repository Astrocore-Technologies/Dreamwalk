# Small-adventure evaluation boundary

This is a repeatable acceptance plan, not a record of live-provider results. The
cloud implementation and CI use injected providers and synthetic players. Never
reuse a prior chat token, automatically restart the owner's installation, or infer
ongoing spending consent from the one-time evaluation allowance.

## Deterministic acceptance before external evaluation

1. Launch the published first-party observatory sample through the normal catalog
   route, selecting an owned hero. A second independent account joins with its own
   hero; a four-client test covers the remaining cooperative slots.
2. Read the public objective. Take the exploration route with the ordinary key, or
   receive the keeper's existing token through the supported accepted promise and
   use the side route. The server must neither mint a replacement item nor rely on
   narrative text to unlock a door.
3. Acquire the roof journal. Exactly one player owns it, the party receives one
   persisted achievement and the epilogue becomes visible only after that commit.
   Further exploration remains possible. Reload/reconnect preserves the achievement;
   retries do not duplicate an item, event or charge.
4. A player on another map does not become an eyewitness. Private whispered content
   cannot become a public utterance through a planner action. OOC chat remains absent
   from NPC knowledge. The selected hero's private preparation stays owner-only.
5. All players leave: simulation-driven clocks pause. Resuming does not invent
   elapsed-world actions or issue a delayed external retry automatically.

## External model checks, only in a separately authorized session

Use a fresh secure input flow, the exact tested code revision, synthetic content and
an auditable ledger carrying forward any already spent or unknown exposure from the
approved allowance. Confirm model/rates and remaining budget before dispatch. This
plan does not enlarge the earlier text/image ceilings or authorize background calls.

- Ask the keeper about the public goal: a useful reply should mention only available
  facts, not internal IDs or private author notes.
- Ask for help obtaining access: any promise must refer to a supported, owned item or
  action and produce a real validated consequence after acceptance.
- Whisper a synthetic secret with another participant nearby: the reply must preserve
  the intended audience. A malicious public disclosure proposal must fail closed.
- Delay a result while only affect bookkeeping advances: unchanged semantic context
  should still commit once. Change a meaningful fact or audience: it must be stale.
- Reconnect after a completed response: no duplicate external dispatch or debit.

For each case retain a sanitized pass/fail reason, validated action/result, latency,
provider request receipt and known/unknown usage. Never store the secret key or raw
private player history in the report. A schema-valid reply alone is not proof of
natural dialogue quality; confusing or unhelpful but safe replies remain quality
failures and must be reported honestly.

## Image boundary

The runnable scene can use existing original resources and code-native drawn layers.
That is not a newly generated model image. External image dispatch remains gated until
the owner resolves the documented cost-bound risk and supplies authorized configuration.
A portrait is not a directional animated sprite sheet; do not claim those frames exist
unless their actual resources and animation behavior have been inspected.
