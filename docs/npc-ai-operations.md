# NPC AI: безопасная эксплуатационная граница

## Что включено сейчас

По умолчанию `NpcAiService` использует локальный mock, цена и провайдерский бюджет равны нулю. Обычный routine tick бесплатен и не вызывает модель на каждом шаге. Значимые события могут создавать ограниченную decision job: локальный mock либо настроенный внешний provider только внутри явно разрешённого sponsor budget; неявных расходов нет. Настоящие API, покупка валюты и изображения **не подключены и не проверялись платными запросами**. Тесты HTTP-адаптера используют подставной локальный transport; интеграционные тесты — отдельный PostgreSQL.

Планировщик получает только серверно отфильтрованные знания NPC. Отдельный запрос публичной речи получает только разрешённые утверждения и фактическую аудиторию; закрытая память планировщика туда не переносится. Summary является производной от доказательств и проверяется ядром. Никакой ответ модели не исполняется как JavaScript/SQL. Изменения мира и списание резервов совершаются в одной транзакции runtime после повторной авторизации и проверки read set.

## Настройки будущего внешнего провайдера

Это отдельные серверные `NPC_AI_*` параметры, не клиентские настройки. Платформенный `AI_PROVIDER` и платежные флаги остаются в прежнем mock-режиме. Следующие значения описывают интерфейс, а не разрешают включение платных вызовов:

| Переменная                                            | Безопасное значение по умолчанию / назначение                                 |
| ----------------------------------------------------- | ----------------------------------------------------------------------------- |
| `NPC_AI_PROVIDER`                                     | `mock`; другие варианты `http-json`, `openai-responses`                       |
| `NPC_AI_EXTERNAL_APPROVED`                            | `false`; только после отдельного согласования бюджета и провайдера            |
| `NPC_AI_ENDPOINT`                                     | отсутствует; точный HTTPS endpoint доверенного сервера                        |
| `NPC_AI_ALLOWED_ORIGINS`                              | пусто; список точных origin через запятую                                     |
| `NPC_AI_API_KEY`                                      | отсутствует; только серверное хранилище секретов                              |
| `NPC_AI_MODEL`, `NPC_AI_VERSION`                      | оператор выбирает модель и версию договора                                    |
| `NPC_AI_COST_CEILING_ATTESTED`                        | `false`; оператор подтвердил, что endpoint соблюдает переданные лимиты        |
| `NPC_AI_UPPER_MICROS`, `NPC_AI_CAP_MICROS`            | `0`; верхняя оценка запроса и общий провайдерский лимит в целых микроединицах |
| `NPC_AI_CREDIT_PRICE`                                 | `0`; отдельная заранее показанная цена операции в демонстрационных Искрах     |
| `NPC_AI_TIMEOUT_MS`                                   | `8000`, допустимо 100–60000                                                   |
| `NPC_AI_MAX_INPUT_TOKENS`, `NPC_AI_MAX_OUTPUT_TOKENS` | 16000 / 1024; передаются endpoint как обязательные ограничения                |
| `NPC_AI_KILL_SWITCH`                                  | `false`; `true` блокирует новые запросы и применение ответов                  |

`http-json` — **не утверждение о совместимости с OpenAI API**. Запрос содержит `model`, `purpose`, `context`, `operationId` и `limits`; ответ содержит `proposal`, `requestId`, `usage:{inputTokens,outputTokens,costMicros}`. Для выбранного реального провайдера потребуется подтверждение договора/адаптер и отдельный разрешённый smoke test. Выбор http-json без explicit approval оставляет внешние вызовы выключенными. Неполная разрешающая конфигурация не запускается.

URL не задаётся игроком. Запрещены IP literals (включая IPv6), credentials, query/hash, localhost/local/internal и редиректы. Exact allowlist — граница доверия к серверному оператору, **не DNS pinning и не универсальная защита от смены DNS доверенного домена**. Оператор обязан контролировать endpoint и его DNS/egress. Текст ошибок не содержит ключ, запрос, ответ или память.

## Состояния и деньги

Долговечная задача проходит `reserved → running → result_received → committed`; возможны `stale`, `cancelled`, `failed`, `reconciling`. Значения queued/validated предусмотрены схемой, но отдельного обязательного сохранённого шага не требуют. Один живой запрос NPC ограничен SQL unique index; claim сериализуется advisory lock кампании, в кампании одновременно выполняется один provider request. Повтор operation ID с тем же публичным намерением возвращает прежний DTO даже при изменившемся мире; смена канала речи/адресата/согласия конфликтует.

Quote действует ограниченное время, используется один раз, а выдача ограничена 60 запросами пользователя в минуту. Wallet.balance не уменьшается при резервировании; доступно `balance − held`. Любые старые административные списания учитывают held. Capture добавляет ledger с уникальным source key и применяется ровно один раз. Ошибка, stale, отзыв доступа или истечение резерва освобождает hold; поздний результат не создаёт новое согласие и не списывает валюту. Принятый cache hit повторно не оплачивается; ключ включает кампанию, NPC, purpose, полный context fingerprint, версии модели и policy.

Провайдерский учет независим: `reserved + spent + unknown ≤ cap`. Непонятный исход сети учитывается как unknown на всю верхнюю оценку, а не как бесплатная ошибка. Нет слепого автоматического повтора. Реальный отчёт выше верхней оценки записывается полностью на задаче; `overrun` хранит превышение отдельно, breaker блокирует весь provider ID. Это учётный hard cap, **не гарантия, что сторонний сервер физически не выставит неверный счёт**. Отмена пользовательского списания не стирает стоимость провайдера.

`reconcile(jobId,eventKey,actualMicros|null)` — внутренний операторский метод, не игровой endpoint. Он требует подтверждённого результата и идемпотентного ключа. При превышении лимита часть до upper относится в spent, превышение остаётся в overrun; breaker не снимается автоматически. После изменения финансовой политики оператор должен разбирать инцидент, пересчитать лимит/расход и отдельно разрешить возобновление. Простая смена версии/рестарт не сбрасывает счётчики. `GET /api/v1/admin/npc-ai/metrics` требует действующую администраторскую сессию; внутренний `metrics()` возвращает только агрегаты состояний/возраст и бюджетные счетчики, без prompts/секретов/личных идентификаторов. Дополнительно возвращаются средняя/максимальная задержка последних 10 000 результатов, число hot observations, причин в очереди и активных обязательств в выборке первых 1000 кампаний, а также число архивных эпизодов. Размер выборки указан явно; каждый SQL-запрос ограничен statement timeout 2 секунды. Это ручная диагностика администратора, не опрос на каждом игровом tick.

## Пауза, рестарт, отзыв доступа и удаление

При всех игроках offline новые provider requests не стартуют и готовые результаты не изменяют мир. Уже отправленный запрос может завершиться и сохраняется; применение ждёт возвращения, повторной авторизации и проверки контекста. Технические сетевые timeout и время финансового резерва остаются wall-clock: фоновая bounded maintenance освобождает просроченные holds даже без игровых ticks. Это не продвижение игрового времени.

После аварии сохранённый running не запускается повторно. По истечении deadline задача становится reconciling; выяснение расхода не зависит от присутствия игроков. Изменение policy/provider version делает ещё не отправленный запрос stale. Отзыв членства/доступа к исходному произведению помечает задачи долговечно, поэтому revoke→reinvite не оживляет старый план. SQL triggers аннулируют cache соответствующей кампании. Повторная авторизация непосредственно перед commit остаётся обязательной.

Удаление данных обнуляет приватные context/proposal/cache и персональные ссылки, освобождает hold, но сохраняет консервативные spent/unknown и обезличенные финансовые записи. Уже отправленный запрос без доказанного результата остаётся потенциальным расходом. Экспорт возвращает пользователю только метаданные его задач, не память другого NPC/игрока.

## Проверки

`GAME_TEST_FILE=integration-ai-orchestration.test.mjs npm run test:game:integration` поднимает отдельный локальный PostgreSQL, не трогая preview. Проверяет конкурентные резервы, защиту admin debit, rollback/capture/replay, неизвестный исход, restart, поздний ответ, pause, технический expiry, версии, cache, revocation/erasure, breaker/reconciliation и подставной HTTP transport. Сквозные маршруты планирования/summary/речи дополнительно проверяются runtime suite. Живой провайдер, его фактическая тарификация и качество речи остаются отдельным этапом после разрешения пользователя.

## Конкретный OpenAI Responses adapter

Дополнительно реализован `NPC_AI_PROVIDER=openai-responses`, а не только generic HTTP-класс. Он использует фиксированный `https://api.openai.com/v1/responses`, JSON body с `model`, `instructions`, `input`, `max_output_tokens` и `text.format={type:'json_schema',strict:true,...}`. `store:false`, `stream:false`, tools/previous_response_id отсутствуют; автоматических повторов нет. Модель обязана быть явно указана в `NPC_AI_MODEL`; названия и цены из чужих скриншотов не подставляются.

Для разрешения OpenAI требуется отдельный `NPC_AI_PRICING_VERIFIED=true`, а не generic `NPC_AI_COST_CEILING_ATTESTED`: OpenAI API не получает наш monetary maxCostMicros. Обязательны проверенные оператором целые ставки `NPC_AI_INPUT_MICROS_PER_MILLION` и `NPC_AI_OUTPUT_MICROS_PER_MILLION` (USD micro-units за миллион соответствующих токенов). До разрешённого live smoke test эти значения не задаются, ключ не используется, adapter остаётся отключённым. Cached input консервативно считается по полной входной ставке. Такой cost помечается provider_cost_evidence=configured_rates: это оценка по фактическому usage и настроенным ставкам, не подтверждённый invoice. Generic endpoint может вернуть reported cost. Операторская финансовая сверка остаётся отдельной. `usage.output_tokens` учитывается целиком, без вычитания reasoning. Официальная документация указывает, что `max_output_tokens` ограничивает также reasoning/non-visible tokens: [Reasoning](https://developers.openai.com/api/docs/guides/reasoning), [Counting tokens](https://developers.openai.com/api/docs/guides/token-counting).

Ответ разбирается как Responses envelope: `id`, `status`, `usage.input_tokens/output_tokens`, `output[].content[]`. Refusal, incomplete и неверный JSON не становятся игровым действием; если usage известен, расход сохраняется, а пользовательский резерв освобождается. Неизвестный usage/сетевая ошибка остаются reconciling без слепого retry; доступный request/response ID сохраняется для операторской сверки. При `store:false` автоматическое получение потерянного ответа не обещается: требуется подтверждённая сверка провайдерского журнала/счёта. Реальный доступ аккаунта, тариф и точность оценки ещё должны быть проверены отдельно.

Строгие схемы различны для plan, summary, speech и intent. План возвращает только до трёх типизированных действий; revisions и target read set восстанавливаются сервером из разрешённого контекста. Summary возвращает только selectedObservationIds; runtime пересобирает fingerprint/range/narrative/version по выбранным существующим доказательствам перед core validation. Модель не задаёт эти поля. План дополнительно может предложить до четырёх revisions убеждений с evidence IDs; knowledgeRevision берётся из серверного контекста, а ядро проверяет CAS, источник и допустимость confidence. Публичная речь получает только отдельный разрешённый speech context, не закрытую память planner. Формат основан на [официальной документации Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs); соответствие схеме не заменяет проверки игровых правил.

`contextBudgetBytes()` вычисляет allowance с учётом capped output, полной сериализованной формы запроса (instructions/schema/model), дополнительного резерва 4096 на framing и двойного JSON escaping. Runtime может удалять только целые необязательные эпизоды до окончательного hash; обязательный вопрос/цель/доказательства обещаний не разрезаются. Финальная защита adapter проверяет реальный размер UTF-8 body, не деление символов на четыре. Гарантированы локальный byte limit и configured accounting bound. Соответствие byte estimate конкретному живому tokenizer/скрытому provider overhead требует smoke verification; это не универсальная гарантия внешнего счёта. Полученный usage сверх рассчитанного token ceiling блокирует provider; cost overrun также сохраняется в независимом budget breaker.

## Явное спонсорство кампании

`npc_ai_sponsors` — долговечное согласие владельца кампании, а не подставной пользователь для system jobs. Grant требует `consent:true`, идемпотентный operation ID, срок не больше 24 часов, разрешённые purposes, общий и пооперационный лимит Искр, число попыток и общий/пооперационный провайдерский предел. Он закрепляет provider/version/policy. Один grant активен на кампанию; новый не заменяет старый без отзыва/истечения. Viewer/чужой участник не может назначить плательщика.

System-origin job хранит requester=null и отдельно payer из grant. Queue проверяет текущее членство/доступ плательщика и остаток бюджета, резервирует его wallet ровно один раз; capture повторно проверяет действительность согласия. Одна общая генерация не оплачивается каждым зрителем. Provider allowance и число попыток расходуются консервативно уже при принятии задачи, без возврата после ошибочного/отменённого запроса; пользовательские Искры учитывают только held/captured. Это исключает бесконечные бесплатные попытки при нулевой цене в Искрах.

Revoke, expiry, source/member revocation и erasure отменяют pending jobs и не оживляют consent при последующем invite. Пауза мира не продлевает финансовое согласие. При отсутствии согласия, лимита или доступного provider мир продолжает бесплатные типизированные routine/mock действия; молчаливого платного fallback нет. Все пределы/остатки/срок возвращаются безопасным DTO без раскрытия памяти или других плательщиков. `exportNpcAiSponsors` экспортирует собственные согласия; erasure удаляет payer-ссылку и отзывает grant, не стирая консервативный финансовый учёт.

## Player intent и атомарный claim

Purpose `intent` имеет subjectKind=player, origin=user и реального requester; legacy поле npcId в внутреннем DTO содержит реальный actor ID. Это не искусственный NPC. Авторизация сверяет actor с membership, а context содержит только видимую игроку сцену/инвентарь/вопрос. Adapter возвращает поддерживаемое действие либо код уточнения AMBIGUOUS/UNSUPPORTED. Получение и оплата допустимого предложения не выполняют действие: runtime сохраняет предложение, показывает его игроку и повторно проверяет состояние при отдельном подтверждении. Sponsor может оплатить предложение, но не подменяет инициатора.

QueueDecision.runtimeRequestId атомарно проверяет и блокирует долговечный queued request, сверяет campaign/subject/purpose/context hash и записывает scheduled+job_id в той же транзакции, что и резерв. Дубликат возвращает прежнюю задачу; canceled request не создаёт новый hold после revoke/reinvite.

## Ограниченное техническое хранение

Фоновая maintenance раз в минуту удаляет private context и proposal терминальных/неопределённых задач старше семи дней: до 1000 строк за проход, SKIP LOCKED и SQL timeout 2 секунды. `reconciling` не означает вечное хранение текста. Не удаляются ledger, receipt/request ID, usage, статус финансовой сверки и reserved/spent/unknown counters; неизвестный расход не становится нулевым из-за retention. Активные/ещё не применённые результаты этим проходом не очищаются. Истёкший cache очищается глобально, даже если в кампанию никто не вернулся. Это технический default, а не утверждение о юридическом сроке финансовых документов; подтверждённое удаление персональных данных остаётся отдельной немедленной процедурой.

Изменения формата request metadata совместимы со старыми PR6 jobs: отсутствующие sponsor/runtime fields трактуются как null, повтор старого operation ID с тем же публичным намерением не создаёт нового резерва. Изменённые предмет, purpose, контекст или согласие по-прежнему конфликтуют.

Планировщик может предложить `communicate` только через recipient ID, канал и 1–4 observation IDs. Никакого сырого текста или secret IDs из private planner в действие не переносится; core заново проверяет фактическую аудиторию и disclosure policy. Выбор идентификатора не является разрешением раскрытия.
