# Per-request text context and reply limits

The requested total window is `text.contextBudgetTokens`; 256000 is only an example,
not a product maximum. The model
capacity remains `text.contextTokens`; the effective window is the smaller value.
`text.maxOutputTokens` reserves reply space inside that window. These settings do
not change cumulative money caps or apply to image generation. No request is padded
to fill the selected context and no session-wide token allowance is consumed.

A token counter measures the complete provider envelope, not only player prose.
The adapter contract separates model capabilities, counting and pricing. Exact
counters must explicitly support the selected model and identify their version;
unsupported models use a labelled conservative estimate. There is currently no
verified local GPT-6 Luna tokenizer in this repository. The ordinary OpenAI path
therefore counts complete UTF-8 envelope bytes plus at least 4096 protocol tokens
as a conservative estimate. This can reach the configured limit before the real
model tokenizer. For example, 130000 Cyrillic letters occupy 260000 UTF-8 bytes;
that is not evidence that a 130000-token model prompt fits or has been tested.

OpenAI documents `POST /v1/responses/input_tokens` for exact request counts:
https://developers.openai.com/api/docs/guides/token-counting . It is not silently
called while quoting, typing or idling. No model-specific exactness is inferred
from another tokenizer, and the synthetic exact counter in tests is not a GPT
implementation. The explicit manual preflight below now integrates this endpoint;
actual account/model access remains unverified without an owner-triggered live test.

The former 64 KiB gate no longer defines this explicit window mode. A separate
4 MiB transport safety limit fails oversized requests rather than cutting strings.
Legacy profiles keep their existing behavior and financial history. Adding or
changing the window requires the normal reviewed policy revision on the same
scope; it cannot clear old spending, unknown charges, holds or permanent stops.

Story context retrieves committed, audience-authorized feed records and old shared
narrative turns. NPC context retrieves only that NPC's own archived observations.
Shared speech excludes private facts and other participants' whispers through the
existing disclosure implementation. OOC party chat is never model history.
Retrieval has a bounded 32768-record candidate guard. Packing keeps whole records,
with older optional history removed first; canon, current scene/rules, current
questions, goals/obligations and their referenced evidence remain pinned. Existing
grounded summaries are reused; no paid summarization or hidden retry is introduced.
If required content alone cannot fit, the request fails before dispatch. Selection
never deletes database history. An admitted manual request retains its exact body
and pricing snapshot while another request or policy revision is pending.

Verification distinguishes growing estimated context, a synthetic exact adapter,
real PostgreSQL admission, and real provider behavior. Offline tests and fake
receipts do not prove a real 130k-token Russian conversation or real image quality.

## Explicit asynchronous preflight

Migration 038 stores count operations separately from generation jobs. In a campaign's
world phase, the configured owner loads pending requests with a read-only GET. Each
request exposes its count pricing gate, candidate fingerprint, attempt count and last
receipt. No GET, render, history packing, startup, worker tick or idle poll calls OpenAI.
The full audience-authorized candidate is retained before approximate byte packing.
Internal candidate/proof metadata is removed from model input.

`POST /api/v1/generation/campaigns/:id/requests/:requestId/preflight` requires explicit
consent, a UUID operation ID, current phase/policy fences and the displayed candidate
fingerprint. The server calls only `/v1/responses/input_tokens`, with supported input
fields including instructions and JSON schema. It reserves reply tokens separately.
The immutable operation binds its source/body hashes, model, provider version, policy
revision/hash and phase. A successful count that fits adopts the full candidate and
its evidence. Quote, consent and dispatch reuse that evidence; changed input, model,
policy or phase fails closed. Nothing is generated by the preflight itself.

The count response does not establish a provider invoice amount. **Counting pricing
is currently unverified for this installation.** Without a separate owner-reviewed
fixed-rate policy, real count calls fail with `TEXT_COUNT_COST_REVIEW_REQUIRED`.
There is no default zero price. A future `text.counting` policy must contain
`kind: "owner_reviewed_fixed"`, an explicitly verified `microsPerRequest` and `pricing`
source/review/expiry evidence. Never enter a guessed rate merely to enable the button.
The ordinary reviewed policy amendment applies this setting on the existing financial
scope. The UI shows it separately from generation pricing and warns that token-count
precision does not establish invoice precision. Existing disabled examples do not
supply or activate this policy.

Each admitted count first reserves its reviewed fee as text usage on the same ledger.
A successful response settles that configured rate once; its cost basis remains
`owner_reviewed_fixed_rate`, not provider-reported invoice evidence. Any error, HTTP
403, ambiguous outcome or deadline stops further dispatch without automatic retry and
retains unresolved reservations. An interrupted operation is never resumed by sending
it again. `GET /api/v1/generation/text-counts/operations/:operationId` reconciles status
without a provider call, including after restart. Browser operation IDs are retained
per account/campaign/request across reload until the result is known.

If a count exceeds the window, no generation is authorized. The owner may explicitly
choose a smaller recent-history record count and request another preflight. Required
question/goal/obligation evidence remains pinned, and database history is untouched.
There are at most three explicit counts per pending request, never an unbounded binary
search against the provider. Unknown jobs or financial stops cannot be bypassed with a
policy revision. Erasure removes input hashes and retains financial liabilities.

Offline verification exercises the actual PostgreSQL authority, reviewed policy,
count transport, persisted evidence, normal quote/consent/dispatch and shared ledger.
Synthetic count receipts do not demonstrate real Luna tokenization or account access.
