# Story discovery popularity

Public cards expose `likeCount`, `totalRounds` and `likedByMe`. Favorites remain independent library bookmarks. No seeded popularity, views, AI calls, narrative submissions, starts, player count or current-round number are used as completed rounds.

The popular ordering is lexicographic: active users' likes descending, completed rounds descending, story creation time descending, story ID ascending. It is evaluated from current database data for every request. Thus a newer empty story wins an otherwise empty tie; editing a story does not boost it. There is no undocumented weighted score or paid boost.

Rounds are persisted server event rows of kind `turn.world.completed` (one completed full player/world cycle) or `round.resolved` (one legacy encounter round). These runtime modes are mutually exclusive. Counts span campaigns and approved playable source versions of the currently public, nonarchived story. Events before the source version was approved, unapproved private/playtest versions, deleted campaign owners and deleted story authors are excluded. Only totals are exposed, never campaign IDs, participants, state, event payloads or private conversation. A source with an existing approved public snapshot remains discoverable while a separate draft is edited, matching existing publication semantics. Private/withdrawn/archived stories expose zero counters; unpublished stories cannot receive likes.

`PUT /api/v1/likes/:adventureId` records the authenticated user's single like; duplicate and concurrent requests are idempotent. `DELETE` removes only that user's like, including after withdrawal. Both return `{likeCount, likedByMe}`. Story-row locking serializes mutations and withdrawal, the composite primary key prevents duplicate likes, and separate aggregates prevent multiplying rounds by likes or members. The round-event partial index and existing source indexes bound the scans to relevant story campaigns and event kinds. Account export includes likes and account erasure removes them.

Migration `053_story_popularity.sql` creates the API-owned likes table and round-event index. RLS is enabled with no client policies; the existing migration/API owner is the trusted access path. There is no new Supabase client or security-definer function. Applying this migration to production is a separate release operation.

Verification: `npm run test:home:integration` uses a disposable local PostgreSQL database, real migrations and HTTP API, with all paid providers disabled. Its popularity fixture covers zero counts, ties, duplicate/concurrent likes, own-only removal, authentication, favorites independence, multiple campaigns, event filtering, unapproved versions, soft deletion, withdrawal and archiving. Synthetic event fixtures exist only in the disposable test database.
